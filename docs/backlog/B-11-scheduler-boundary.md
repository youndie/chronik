# B-11 — Судьба petich-scheduler

Модуль `petich-scheduler` перекрывает chronik по названию и расходится по существу в трёх местах:
он исполняет чужой код (`ScheduledJobRunner.run`), он не транзакционен, и он допускает двойной
запуск без инструмента, который бы этот запуск ограничил
([research §1.1](../research/research-architecture.md)). Держать оба — значит держать два ответа на
вопрос «переживёт ли этот таймер рестарт».

- **Гипотеза: слой совместимости дешевле устаревания**, потому что календарная арифметика
  (`ONCE / DAILY / WEEKLY / MONTHLY`, «то же число следующего месяца» с таймзоной) у него уже
  написана и проверена, а chronik её сознательно не имеет (D5). **Проверить на вехе M3**, когда
  станет видно, во что обходится `ScheduledJobRunner` поверх примитива, который чужой код не
  исполняет.
- Побочная находка, которую стоит закрыть независимо от исхода: у эталонного потребителя таблица
  `scheduled_jobs` заведена миграцией и живёт в схеме, а планирует в неё **никто** — модуль
  подтянут по зависимости, в сборке сервера не объявлен, и в схемном тесте фигурирует только его
  таблица. Пустая таблица, которую поддерживают миграции ради модуля, которым не пользуются.
- Не покрывает: сам мост — это [B-10](B-10-petich-bridge.md).

- AC: решение записано в ресёрч по месту (§1.1 или новый пункт), с причиной и отвергнутым
  вариантом, а не только в этом файле.
- AC: если выбран слой совместимости — существующий API `ScheduledJob` продолжает работать без
  изменений на стороне приложения; если устаревание — есть путь миграции, а не только пометка.
- Anchors: `petich/petich-scheduler/src/commonMain/kotlin/`, `petich/settings.gradle.kts`
