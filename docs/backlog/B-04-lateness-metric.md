# B-04 — Опоздание считается и выходит наружу

Таймер, чей срок прошёл, пока процесс лежал, срабатывает при старте — это штатный исход, а не
ошибка (D7). Величина опоздания — единственное число, по которому видно, что воркер жив и
справляется: латентность доставки сама по себе не отличает «сработал вовремя» от «взял через сорок
минут после срока».

- **Решение: опоздание — наблюдаемая величина в API воркера (`onFired(id, lateness)`), а не
  строка лога.** Логи агрегируются иначе в каждом приложении, а метрика должна собираться
  одинаково. Форма — `PetichEngineMetrics`: no-op по умолчанию, ничего не стоит.
- Вместе с ним наружу выходит проигравший в гонке за аренду. Аренда, у которой не видно
  проигравших, неотличима от аренды, которая никогда не срабатывает — так это сформулировано у
  потребителя, написавшего заявку руками
  ([research §1.4](../research/research-architecture.md)).
- Не покрывает: сбор в конкретную систему метрик — это работа приложения.

- AC: после рестарта с просроченными таймерами каждое сработавшее событие несёт ненулевое
  опоздание, и его видно снаружи без чтения логов.
- Anchors: `chronik-core/src/commonMain/kotlin/`
