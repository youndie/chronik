# B-03 — Ядро: три операции и транзакционный шов

`schedule(id, at, payload)`, `cancel(id)`, `reschedule(id, at)`. Cancel и reschedule —
первоклассные операции, а не «новый таймер и флаг у старого»: продление срока в потребителе есть
одно изменение одной строки, и всякий обход этого расходится с состоянием при первой же гонке.

Транзакционный шов — единственное, ради чего chronik существует. Запись таймера должна попадать в
транзакцию **вызывающего**, ровно как `ExposedPetichRepository.update` пишет сагу и outbox одним
`suspendTransaction`.

- **Решение: тип отказывается собрать планировщик на хранилище, которое не умеет писать в чужую
  транзакцию.** Не предупреждение в логе — отказ, по образцу `PetichEngineConfig(requireOutbox =
  true)`. Причина в [research, риск 1](../research/research-architecture.md): провал этого шва
  невидим — состояние верное, сага завершилась, не сработает только то, чего никто не ждёт сейчас.
- Отвергнуто: свой пул и своё соединение внутри chronik. Тогда транзакция чужая по построению, и
  гарантия теряется — это и есть отличие от «сервиса таймеров».
- Не покрывает: сам Postgres-бэкенд — это [B-05](B-05-postgres-backend.md).

- AC: попытка собрать планировщик на хранилище без транзакционного контракта падает при сборке
  объекта, а не при первом `schedule`.
- AC: `reschedule` несуществующего id и `cancel` уже сработавшего таймера имеют документированный
  наблюдаемый исход, а не «как получится».
- Anchors: `chronik-core/src/commonMain/kotlin/Chronik.kt`,
  `chronik-core/src/commonMain/kotlin/TimerStore.kt`,
  `chronik-core/src/commonTest/kotlin/ChronikOperationsTest.kt`

## Закрыт 04.09.2026

**Отказ оказался сильнее, чем требовала приёмка.** Конструктор `Chronik` принимает
`TransactionalTimerStore` и ничего слабее, то есть хранилище без транзакционного контракта до него
не доходит вовсе — говорит компилятор, в месте связывания. Приёмка требовала падения при сборке
объекта; получилось падение до запуска. Рантайм-путь остался для случая, который система типов не
покрывает: хранилище, приехавшее из контейнера или фабрики под типом `TimerStore`, — это функция
`chronik(store, clock)`, и она бросает с сообщением, называющим класс хранилища.

Исходы `reschedule`/`cancel` для несуществующего и для терминального таймера теперь не «как
получится», а восемь проверок в `ChronikOperationsTest`. Отдельно закреплено, что отмена **после**
наступления срока, но до выхода события работает: это то самое окно, ради которого компенсация саги
её и зовёт.

**Существенная находка: модель врала, и оракул стоял на ней.** Проверка возврата `reschedule`
считалась до коммита, поэтому `cancel` и следом `reschedule` по одному id в одной транзакции оба
отвечали «true», а второй при коммите тихо не делал ничего. SQL-хранилище так себя вести не может —
его `UPDATE ... WHERE state = 'PENDING'` идёт внутри транзакции, видит отмену и возвращает ноль
строк. То есть модель благословляла ответ, которого у настоящего бэкенда не будет. Транзакция
переписана на overlay: чтения через неё видят её же записи, воркер читает только закоммиченное.
Положительный контроль прогнан — возврат к старому чтению роняет новый тест.

Найдено рассуждением о различии модели и SQL, а не прогоном: прогон был зелёный в обоих случаях.
