# B-09 — Замер: опоздание и деградация скана

Число, которое публикуется: лаг между сроком и срабатыванием, p50/p95, при N таймеров в секунду на
одном ядре рядом с Postgres. И второе: на каком объёме ожидающих строк скан деградирует без
индекса по `due_at` и с ним.

- **Решение: у каждой цифры пишется, что мерялось, чем и на какой машине.** Иначе цифра переезжает
  в README и живёт там дольше, чем условие, при котором была верна.
- **Решение: прогон, где всё прошло, замером не считается.** Нужен вариант, на котором видно
  деградацию, — иначе неизвестно, меряет ли стенд вообще что-нибудь. Отсюда пара «без индекса /
  с индексом» в одном прогоне, а не только целевая конфигурация.
- Один прогон на вариант — не замер: разброс между прогонами здесь того же порядка, что разница
  между вариантами, и первый прогон после перезапуска меряет прогрев.
- Не покрывает: выбор системы метрик приложением.

- AC: в `docs/benchmarking.md` есть строка на каждый вариант с абсолютной величиной, а не только
  с отношением «в K раз быстрее».
- AC: конфигурация без индекса даёт видимо худший результат — положительный контроль стенда.
- Anchors: `chronik-benchmark/src/main/kotlin/`, `docs/benchmarking.md`
