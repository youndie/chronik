# B-12 — Приёмочный набор бэкенда

SQLite-режим для одного бинарника когда-нибудь понадобится, и решается он не «ещё одной
реализацией», а корпусом случаев, который гоняется против любой. Заводить корпус нужно, пока
реализация одна: набор, написанный после второй реализации, описывает их пересечение, а не
контракт.

- **Решение: форма берётся с пары «один корпус против двух реализаций», а не с приёмки чёрным
  ящиком по HTTP.** Второе — форма для серверного режима, и понадобится позже
  ([research §1.6](../research/research-architecture.md)).
- **Решение: проверки копят находки, а не бросают исключение на первой.** Прогон должен доходить
  до конца и показывать всё — иначе вторая реализация чинится по одной находке за прогон.
- Не покрывает: сам SQLite-бэкенд. Он заводится, когда появится потребитель, а не заранее.

- AC: корпус гоняется против Postgres-бэкенда и зелёный; каждая проверка названа правилом
  семантики из [B-01](B-01-semantics-before-code.md), а не номером.
- AC: есть **сторож холостого прогона** — корпус, ничего не проверивший на подсунутой заглушке,
  падает. Иначе зелёный результат второй реализации не отличается от отсутствия проверок.
