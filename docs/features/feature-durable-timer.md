# Долговечный таймер

## 1. Обзор

`schedule(id, at, payload)` записывает срок. В момент `at` — или позже, но **никогда раньше и
никогда потеряно** — наружу уходит факт «пора» с этим payload. Отмена и перенос по id —
первоклассные операции, а не обходы через флаги.

`client_entries: []` и `api: []` — это ответ, а не пропуск: у chronik нет клиента, и в v1 нет
HTTP-поверхности.

## 2. Правила, сформулированные так, чтобы их можно было проверить

* **Не раньше срока.** Событие не выходит при `now < at`. Ни при каких обстоятельствах — это
  единственное строгое обещание, и все остальные слабее.
* **Не потеряно.** Записанный и не отменённый таймер срабатывает — при первой же возможности после
  срока, включая возможность, появившуюся после рестарта.
* **At-least-once.** Событие может выйти более одного раза. Дедупликация — работа получателя по
  idempotency key из payload; ровно-один-раз не обещается ни в API, ни в README (D4).
* **Отмена окончательна.** Отменённый таймер не срабатывает, даже если срок уже наступил, но
  событие ещё не ушло.
* **Перенос — изменение одной строки.** `reschedule(id, at)` меняет срок существующего таймера, а
  не заводит второй и не помечает первый. Продление срока у потребителя — это ровно оно.
* **Единица времени — секунда** (D5), и это выражено в типе публичного API, а не только в тексте.
* **Payload непрозрачен.** Уже сериализованная строка; chronik не знает, что внутри, иначе он
  перестаёт быть переносимым механизмом и становится частью чьей-то фичи.

## 3. Чего chronik не делает

Раздел нормативный: каждый пункт — отказ с номером решения, а не недоделка
([B-01](../backlog/B-01-semantics-before-code.md)).

| Не делает | Решение | Почему |
|---|---|---|
| Не исполняет чужой код | D1 | наружу уходит факт «пора»; исполнение — у слоя выше, и это отличие от `petich-scheduler` |
| Не открывает своё соединение | D2 | транзакция обязана быть чужой — иначе теряется единственная причина существования |
| Не обещает ровно-один-раз | D4 | честной альтернативы (распределённой транзакции с приёмником) нет |
| Не имеет календаря и таймзон | D5 | календарь уже есть в `petich-scheduler`; второе место с той же арифметикой не нужно |
| Не догоняет пропущенные периоды | D6 | для работы с побочными эффектами догонять опаснее, чем пропустить |
| Не повторяет бизнес-логику | D9 | ретраи здесь доставляют событие; провал операции компенсирует тот, кому она принадлежит |

## 5. Сценарии

Все сценарии **целевые**: пути срабатывания ещё нет. Перед слиянием в `main` каждый сверяется с
настоящим поведением — с настоящими типами и настоящими сообщениями об ошибках, а не с этим
текстом.

**Почему ни на одном сценарии пока нет строки `**Automated:**`, хотя тесты уже есть.**
`TimerBoundaryTest` проверяет `Timer.isClaimableAt` и `Timer.latenessAt` — предикат, а не путь: ни
воркера, ни хранилища, ни приёмника он не касается. Сценарий «раньше срока не срабатывает никогда»
говорит о событии, вышедшем наружу, и предикатом не проверяется. Пометить его автоматизированным
значило бы записать в отчёт покрытие, которого нет, — и отличить это потом было бы нечем.

### Scenario: таймер срабатывает после срока

* **Given:** записан таймер `t1` со сроком `at`
* **When:** часы дошли до `at`
* **Then:** наружу выходит событие с payload таймера `t1`
* **And:** событие не выходило ни разу при `now < at`

### Scenario: раньше срока не срабатывает никогда

* **Given:** записан таймер `t1` со сроком `at`
* **When:** воркер сделал произвольное число проходов при `now < at`
* **Then:** событий нет

### Scenario: отмена после наступления срока, но до выхода события

* **Given:** таймер `t1` со сроком, который уже наступил, и воркер ещё не сделал прохода
* **When:** вызван `cancel("t1")`
* **Then:** событие не выходит ни при одном последующем проходе

### Scenario: перенос не создаёт второго таймера

* **Given:** таймер `t1` со сроком `at1`
* **When:** вызван `reschedule("t1", at2)`, где `at2 > at1`
* **Then:** в момент `at1` событий нет
* **And:** в момент `at2` выходит **ровно одно** событие

### Scenario: отмена несуществующего id

* **Given:** таймера с id `nope` нет
* **When:** вызван `cancel("nope")`
* **Then:** наблюдаемый исход документирован и одинаков при повторе — не исключение в одном случае
  и молчание в другом

### Scenario: одно и то же множество при любом чередовании операций

* **Given:** произвольная последовательность `schedule` / `cancel` / `reschedule` и убийство
  процесса в произвольной точке между «строка записана» и «событие ушло»
* **When:** система доведена до состояния, где сроки всех таймеров в прошлом
* **Then:** множество сработавших равно множеству «дошли до срока и не отменены»
* **And:** ни одно не сработало раньше своего срока, и опоздание каждого посчитано

Это спека целиком; остальные сценарии — её частные случаи, оставленные читаемыми.
